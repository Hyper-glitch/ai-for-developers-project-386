# Шаг 1. Результат: анализ референса и требования

Документ фиксирует итог первого шага: как устроен пользовательский путь в Cal.com, что из него берём, что обязано быть в приложении, какие ограничения действуют и что требуется от генерации клиента. Стек и детали реализации здесь не выбираются — это следующий шаг.

## 1. Референс: путь в Cal.com

Путь восстановлен по описанию задания и публичному интерфейсу Cal.com. Регистрация, внешние календари и уведомления в задание не входят и пропущены.

**Владелец**
1. Раздел «Event Types» → «New»: вводит название, описание и длительность (например, 30 минут). Сохраняет.
2. Раздел «Availability»: задаёт рабочие часы по дням недели и часовой пояс.
3. Получает публичную ссылку на свою страницу со списком типов встреч.
4. Раздел «Bookings» → «Upcoming»: видит список предстоящих встреч с датой, временем, типом и именем гостя.

**Гость**
1. Открывает публичную страницу владельца и видит список типов встреч (название, описание, длительность).
2. Выбирает тип → открывается календарь: дни с доступными слотами выделены, недоступные приглушены.
3. Выбирает день → справа появляется список стартов слотов.
4. Выбирает время → форма: имя, email, комментарий (необязательно).
5. Подтверждает → экран «Встреча запланирована» с итогом: тип, дата, время, длительность.

## 2. Что берём и что отбрасываем

| Возможность Cal.com | У нас |
|---|---|
| Типы встреч: название, описание, длительность | Берём |
| Публичная страница со списком типов | Берём, без регистрации гостя |
| Календарь с доступными днями и слотами | Берём, окно 14 дней |
| Форма бронирования и экран подтверждения | Берём |
| Список предстоящих встреч владельца | Берём, по всем типам сразу |
| Авторизация, несколько пользователей, команды | Нет, владелец один и задан заранее |
| Настройка расписания через интерфейс | Нет, часы работы и часовой пояс фиксируются в спецификации |
| Внешние календари, видеосвязь, уведомления, email | Нет |
| Отмена и перенос встреч, платежи, буферы, лимиты | Нет |

## 3. Сценарий от создания типа до записи у владельца

1. Владелец создаёт тип встречи «Знакомство», 30 минут, с описанием.
2. Гость открывает страницу записи и видит «Знакомство» в списке типов.
3. Гость выбирает тип и видит календарь на 14 дней вперёд со свободными слотами по 30 минут.
4. Гость выбирает день и время, вводит имя и email, подтверждает.
5. Гость видит подтверждение записи. Выбранный слот у всех пропадает из свободных — и для этого типа, и для остальных типов, если интервалы пересекаются.
6. Владелец открывает список предстоящих встреч и видит новую запись: тип, дата, время, имя и email гостя.

Тот же сценарий в кратком виде добавлен в `README.md`.

## 4. Обязательные функции

**Владелец**
- Создать тип встречи: название, описание, длительность.
- Посмотреть список своих типов встреч.
- Посмотреть список предстоящих встреч всех типов, отсортированный по времени.

**Гость**
- Посмотреть список типов встреч.
- Посмотреть свободные слоты выбранного типа на 14 дней вперёд.
- Забронировать свободный слот, указав свои контакты.
- Получить подтверждение или понятную ошибку, если слот уже занят.

## 5. Правила бронирования

- Окно записи — 14 календарных дней, сдвигается вместе с текущей датой.
- Длительность слота равна длительности типа встречи.
- Старты слотов идут с фиксированным шагом.
- Слот целиком помещается в рабочие часы владельца.
- Слоты в прошлом не показываются и не бронируются.
- Пересечение двух встреч запрещено, в том числе частичное и между разными типами.
- Встреча может начаться ровно в момент окончания предыдущей (интервалы полуоткрытые: `[начало, конец)`).
- Правила соблюдаются при одновременных запросах: из двух конкурирующих броней на пересекающееся время успешна ровно одна, вторая получает ошибку конфликта.
- Сервер проверяет все правила сам и не доверяет тому, что показал клиент.

## 6. Ограничения приложения

- Нет авторизации и личных кабинетов. Владелец один, задан заранее; его разделы доступны без входа.
- Нет интеграций с внешними календарями и уведомлений.
- Данные можно хранить в памяти процесса. Если так — перезапуск стирает типы и записи, и это нужно указать в `README.md`. Сохранение после перезапуска не требуется для приёмки.

## 7. Решения, которые нужно зафиксировать в спецификации

Задание оставляет их на выбор. Ниже — предложение по умолчанию, окончательно фиксируем на шаге проектирования контракта.

| Параметр | Предложение |
|---|---|
| Начало окна записи | Сегодня (слоты раньше текущего момента скрыты) |
| Часовой пояс владельца | Один фиксированный, например `Europe/Moscow` |
| Рабочие часы | Пн–Пт, 09:00–18:00 |
| Шаг стартов слотов | 15 минут |
| Допустимые длительности | Кратны шагу, например 15–120 минут |
| Формат времени в API | ISO 8601 с явным смещением или в UTC |
| Обязательные поля гостя | Имя и email |

## 8. Требования к API и генерации клиента

- Источник правды — контракт на TypeSpec.
- Из TypeSpec генерируется спецификация OpenAPI.
- Из OpenAPI генерируется клиентский SDK для фронтенда. До выбора языка и фреймворка фронтенда нужно проверить, что для него есть генератор клиента из OpenAPI.
- Если серверный фреймворк умеет генерировать типы и маршруты из OpenAPI — используем это. Если нет — бекенд пишется по контракту вручную и проверяется тестами на соответствие.
- Контракт описывает ошибки: неверные данные, несуществующий тип встречи, слот вне окна или рабочих часов, конфликт времени.
